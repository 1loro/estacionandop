Filosofía de arquitectura

Una sola regla organiza todo el sistema: Next.js + Prisma es el backend — todo el CRUD, la autenticación y las reglas de negocio viven ahí y hablan directo con PostgreSQL. Java no es un segundo backend; son dos calculadoras sin estado que Next.js consulta por HTTP cuando necesita un número que no es una simple lectura de base de datos: un precio sugerido, o una ruta óptima.

Por qué no dos backends completos Duplicar auth, modelos y acceso a datos en dos lenguajes distintos multiplica el trabajo de mantención sin aportar valor al usuario. Los motores en Java no necesitan su propia base de datos: reciben todo el contexto que necesitan en el cuerpo de la petición HTTP y devuelven un resultado — nunca persisten nada por su cuenta.
01

Autenticación y sesiones

No se usa ninguna librería de auth de terceros: el sistema de sesiones está escrito a mano, inspirado en el patrón que popularizó Lucia (hoy descontinuada como paquete). La idea central es que la base de datos nunca guarda un token utilizable, solo su huella.

  • Al hacer login se genera un token aleatorio de 32 bytes (crypto.randomBytes).
  • Ese token se hashea con SHA-256 y el hash es lo que se guarda como llave primaria en sessions.
  • El token original (sin hashear) va en una cookie httpOnly, secure en producción y sameSite=lax.
lib/auth/session.ts
function hashToken(token) {
  return crypto.createHash('sha256').update(token).digest('hex')
}

export async function createSession(userId) {
  const token = generateSessionToken()
  const expiresAt = new Date(Date.now() + SESSION_DURATION_MS)

  // la llave primaria es el HASH, nunca el token real
  await prisma.session.create({ data: { id: hashToken(token), userId, expiresAt } })
  await setSessionCookie(token, expiresAt)
}

Si alguien filtrara la base de datos completa, no tendría ninguna sesión usable: no puede revertir un hash SHA-256 para obtener el token que la cookie realmente necesita.

Renovación deslizante Cada vez que se valida una sesión y le queda menos de la mitad de su vida útil, se le renueva la expiración silenciosamente (sin pedirle al usuario que vuelva a loguearse). Esa escritura de cookie solo puede hacerse desde un Server Action o Route Handler — si la validación ocurre durante el render de un Server Component, el intento de escritura se envuelve en un try/catch y se ignora: la sesión en la BD igual se extiende, la cookie se pone al día en la próxima interacción real.
02

Validación de RUT chileno

El registro exige un RUT válido, calculado con el algoritmo de módulo 11 sobre el cuerpo del número, comparando el dígito verificador obtenido contra el ingresado. No se llama a ningún servicio externo — es una función pura escrita desde cero.

lib/auth/rut.ts
export function isValidRut(raw) {
  const match = /^(\d{7,8})-([\dK])$/.exec(raw)
  if (!match) return false

  const [, body, dv] = match
  let sum = 0, multiplier = 2
  for (let i = body.length - 1; i >= 0; i--) {
    sum += Number(body[i]) * multiplier
    multiplier = multiplier === 7 ? 2 : multiplier + 1
  }

  const remainder = 11 - (sum % 11)
  const expectedDv = remainder === 11 ? '0' : remainder === 10 ? 'K' : String(remainder)
  return expectedDv === dv
}

El multiplicador cicla 2,3,4,5,6,7,2,3… de derecha a izquierda sobre los dígitos del cuerpo — la definición exacta del algoritmo oficial del Servicio de Registro Civil. Combinado con Zod en el schema de registro, un RUT mal escrito nunca llega a tocar la base de datos.

03

Espacios y disponibilidad

La parte más delicada del modelo de datos: separar lo que el dueño ofrece de lo que ya está tomado, para poder mostrarle al usuario únicamente el tiempo realmente libre.

  • Availability: un rango horario amplio que el dueño define ("disponible todo el fin de semana").
  • Reservation: el sub-rango exacto que un usuario reservó dentro de esa ventana — nunca la ventana completa.

Esto significa que una misma Availability de una semana puede tener varias reservas distintas de otros usuarios en distintos días, sin pisarse. Para calcular qué le queda libre a un espacio, se resta cada reserva confirmada de la ventana de disponibilidad con un algoritmo de resta de intervalos:

lib/parking-spots/free-ranges.ts
export function subtractBusyRanges(window, busyRanges) {
  let segments = [window]

  for (const busy of busyRanges) {
    const next = []
    for (const segment of segments) {
      if (busy.end <= segment.start || busy.start >= segment.end) {
        next.push(segment) // no se tocan, queda igual
        continue
      }
      if (busy.start > segment.start) next.push({ start: segment.start, end: busy.start })
      if (busy.end < segment.end) next.push({ start: busy.end, end: segment.end })
    }
    segments = next
  }

  return segments.filter((s) => s.end > s.start)
}

La idea: se parte con un solo segmento libre (toda la disponibilidad) y, por cada reserva ocupada, se recorta en dos pedazos si la reserva cae en medio, o se descarta el pedazo si la reserva lo cubre entero. Un ejemplo con números reales:

Disponibilidad publicada09:00 – 18:00
Reserva confirmada #111:00 – 12:00
Reserva confirmada #215:00 – 16:30
Horarios que ve el usuario09–11 · 12–15 · 16:30–18
04

Reservas sin choques

Restar rangos evita mostrar horarios ocupados, pero no evita que dos personas reserven el mismo minuto a la vez — ese es un problema de concurrencia, no de cálculo.

La condición de carrera Usuario A y usuario B abren el mismo horario libre casi al mismo tiempo. Ambos leen "disponible". Ambos confirman. Sin protección, la base de datos terminaría con dos reservas confirmadas que se solapan — el espacio quedaría comprometido dos veces.

La solución es una transacción con el nivel de aislamiento más estricto de PostgreSQL, SERIALIZABLE, que vuelve a comprobar si existe un solapamiento dentro de la misma transacción, justo antes de insertar:

lib/reservations/actions.ts
await prisma.$transaction(async (tx) => {
  const overlapping = await tx.reservation.findFirst({
    where: {
      spotId: availability.spotId,
      status: 'CONFIRMED',
      startTime: { lt: endTime },
      endTime: { gt: startTime },
    },
  })

  if (overlapping) throw new Error('SLOT_TAKEN')

  await tx.reservation.create({ data: { /* ... */ } })
}, { isolationLevel: Prisma.TransactionIsolationLevel.Serializable })

Si dos transacciones SERIALIZABLE intentan escribir de forma que se contradicen entre sí, Postgres aborta una de las dos con el código de error P2034 en vez de dejar pasar el dato corrupto. Esa señal se atrapa explícitamente y se traduce en un mensaje humano ("alguien más reservó justo ahora, intenta de nuevo") en vez de un error genérico.

Verificado, no solo escrito Se probó disparando dos reservas simultáneas y contradictorias con Promise.all contra la base de datos real: exactamente una se confirma, la otra recibe el error controlado. No es una garantía teórica — se ejecutó.

El precio también se congela en este mismo momento: totalPrice se calcula (horas × precio por hora del espacio) y se guarda dentro de la reserva, en vez de recalcularse cada vez que se muestra. Así, si el dueño sube el precio de su espacio después, las reservas ya hechas mantienen el precio que la persona realmente aceptó pagar — algo indispensable para que la política de cancelación (90% reembolsado, 10% retenido) sea sobre un monto real y estable.

05

Eliminar un espacio con una reserva activa

Regla de negocio explícita: un dueño puede arrepentirse de ofrecer su espacio, pero no puede dejar a alguien sin el estacionamiento que ya pagó.

EstadoSignificado
isPublished=trueVisible y reservable normalmente.
isPublished=false, archivedAt=nullEl dueño lo pausó manualmente — puede reactivarlo.
isPublished=false, archivedAt=<fecha>El dueño lo eliminó, pero queda oculto (no borrado) porque debe una reserva confirmada.

Al "eliminar" un espacio con reservas activas, no se borra el ParkingSpot — se archiva. Y de sus disponibilidades futuras, solo se eliminan las que no tienen ninguna reserva encima (borrar una que sí la tiene arrastraría en cascada el historial de esa reserva):

lib/parking-spots/actions.ts
if (activeReservations === 0) {
  await prisma.parkingSpot.delete({ where: { id: spotId } })
} else {
  await prisma.$transaction([
    prisma.availability.deleteMany({
      where: { spotId, endTime: { gt: now }, reservations: { none: {} } },
    }),
    prisma.parkingSpot.update({ where: { id: spotId }, data: { isPublished: false, archivedAt: now } }),
  ])
}

En la interfaz, esto se traduce en un modal que le explica al dueño exactamente esto antes de confirmar: se eliminará de las búsquedas, pero la reserva pendiente se debe cumplir igual, con una vía de contacto a soporte para el caso excepcional.

06

Fotos y almacenamiento

Las fotos de espacios y avatares se validan antes de subir (solo JPG/PNG/WEBP, máximo 5 MB) y se guardan en Supabase Storage con un nombre aleatorio (crypto.randomUUID()) para que dos usuarios nunca puedan pisarse un archivo.

Bug real encontrado antes de producción El cliente de Supabase (@supabase/supabase-js) intenta construir su cliente de Realtime aunque solo se use Storage, y ese cliente necesita un WebSocket global que Node 20 no trae por defecto — la app se caía al iniciar. Se detectó con una prueba de humo antes de que llegara a un usuario real, y se resolvió inyectando el paquete ws como implementación de WebSocket.
07

Geocodificación, comuna y mapas

Cuando el anfitrión escribe una dirección, un componente de autocompletado consulta la Geocoding API de Mapbox (restringida a Chile) y exige que se elija una sugerencia real — nunca se guardan coordenadas de texto libre sin verificar. De la respuesta se extrae además la comuna por separado, buscando el nivel place del contexto geográfico que devuelve Mapbox:

lib/mapbox/geocoding.ts
function extractComuna(feature) {
  const context = feature.context ?? []
  const byPrefix = (prefix) => context.find((e) => e.id.startsWith(prefix))?.text ?? null

  if (feature.place_type.includes('place')) return feature.text
  return byPrefix('place') ?? byPrefix('locality') ?? byPrefix('neighborhood') ?? null
}

Guardar la comuna en su propia columna (en vez de solo la dirección completa como texto) es lo que permite ofrecer un filtro real de "solo espacios en Providencia" en Explorar — un dato estructurado sirve para filtrar; un párrafo de texto libre no.

Los mapas se dibujan con mapbox-gl directamente (sin envoltorios de React como react-map-gl), cargados dinámicamente con next/dynamic({ ssr:false }) porque la librería depende del navegador y no puede pre-renderizarse en el servidor.

Motor de optimización de ruta

El segundo servicio en Java no calcula rutas desde cero — orquesta las APIs de Mapbox que sí resuelven el problema real de enrutamiento vial, y expone dos operaciones distintas según la pregunta que se está haciendo:

EndpointPregunta que respondeAPI de Mapbox
/api/route/rank"¿Cuál de estos espacios me queda más cerca en tiempo real de viaje?"Matrix (hasta 24 destinos por consulta)
/api/route/directions"¿Cómo llego exactamente al que ya elegí?"Directions (ruta, distancia, pasos)

La geometría de la ruta se devuelve como un string simple "lng,lat;lng,lat;..." en vez de GeoJSON completo — evita depender de una librería de tipos solo para pasar coordenadas, y el frontend la separa con un split para dibujar la línea en el mapa.

Probado con coordenadas reales Se consultó la API real de Mapbox con puntos de Santiago (Providencia, Ñuñoa, Las Condes): el ranking ordenó correctamente por tiempo de viaje real, no por distancia en línea recta — un espacio "más lejos" en el mapa puede ganar si el camino es más directo.
10

Por qué los motores están en un solo servicio Java

Precio y ruta son dos dominios distintos, pero se optan por vivir en una sola aplicación Spring Boot (dos paquetes internos, pricing y routing) en vez de dos microservicios separados. Para el alcance de este proyecto, correr dos procesos, dos puertos y dos despliegues no compra nada — la complejidad operativa de microservicios se justifica cuando equipos distintos escalan cada servicio por separado, que no es el caso aquí.

Next.js nunca llama a estos motores desde el navegador: la llamada ocurre en un Server Action, servidor-a-servidor. Eso evita tener que configurar CORS y mantiene a Mapbox y a la lógica de negocio fuera del alcance del cliente.

11

Seguridad — resumen de decisiones

  • Contraseñas con bcrypt (nunca texto plano, nunca reversible).
  • Sesiones por token opaco + hash: la base de datos nunca contiene un secreto usable directamente.
  • Cookies httpOnly + secure en producción — inaccesibles desde JavaScript del navegador.
  • Validación de todo input con Zod antes de tocar la base de datos, en cada Server Action.
  • Transacciones SERIALIZABLE donde una condición de carrera pudiera vender el mismo espacio dos veces.
  • Ningún motor en Java tiene credenciales de base de datos ni acceso directo a Postgres.
